## 1. Update protocol (read before every contribution)

Every commit, pull request or agent session that changes anything in the repository, including documentation only, must update this file in the same change.

1. **Statuses.** Set the status of every task you touched. `[ ]` todo, `[~]` in progress, `[x]` done, `[!]` blocked (say by what), `[-]` dropped (say why).
2. **Evidence.** A task becomes `[x]` only after you ran its "Done when" check. Put the evidence in the task's `Evidence:` line (command and result, test file, or a link to `docs/spikes/Sx.md`). No evidence, no `[x]`.
3. **New work.** If the change does not match an existing task, add one in the right phase with an ID, priority, owner, estimate and a "Done when". Never leave unplanned work unrecorded.
4. **Discovered work.** Add tasks for follow-ups, bugs and new risks you found, even if you are not fixing them now.
5. **Requirement matrix.** Update the row in section 5 for any PRD requirement affected.
6. **Spikes and decisions.** Update section 6 when a spike moves. Append to section 8 when a design decision changes.
7. **Progress block.** Run `pnpm roadmap` to regenerate the block at the top. Never edit it by hand. CI fails if it is stale.
8. **Changelog.** Add one line to section 9 (newest first): date, author, task IDs, what changed, evidence.
9. **Dates.** Update "Last updated" and "Today's position".
10. **Honesty.** Do not mark work done that is not done. Do not delete a task to make progress look better; mark it `[-]` with a reason.

`A9` is done as of 2026-11-02, so step 7 is no longer manual: `pnpm roadmap` regenerates the block, `pnpm roadmap:check` fails when it is stale, and both halves of that — the passing case and each failing case — have been observed running in GitHub Actions.

Task line format (the script parses it, so keep it exact):

```
- [ ] **C4** [P0] Short description. Reqs: GW-2. Deps: C1, C3. Owner: agent. Est: 3h.
  - Done when: concrete check.
  - Evidence: (filled in when done)
```

Owners: `agent`, `human` or `either`. Estimates are elapsed working hours with agent assistance and are guesses.

## 2. Definition of 100% ready

All of the following are true at once:

1. Every `[P0]` task is `[x]` with evidence.
2. Every P0 requirement in section 5 is done and covered by a passing test or a documented manual check.
3. `pnpm lint && pnpm typecheck && pnpm test && pnpm boundaries && pnpm roadmap:check` pass in CI on `main`.
4. A fresh clone runs `docker compose up` then `pnpm demo` with no keys and exits 0.
5. At least one real mainnet payment was routed through Intents with the result captured, or spike S1 or S7 formally recorded that it cannot be done, with the fallback documented.
6. The README states what is real, what is mocked and the known limitations.
7. The repository is public, contains no secrets and has a license.
8. The demo video and X post are published, the submission form is sent, and the confirmation is recorded in the changelog.
9. The docs match the built system. No open VERIFY marks remain that a spike could have closed.

## 8. Decision log

Append new decisions here (newest first). Design decisions D1 to D14 and their reasoning live in `docs/ARCHITECTURE.md`; record changes to them here too.

- 2026-11-04: **C9: a strike block is per seller, and a clear is a watermark rather than a rewrite.** The design sketch counted `served_unsettled` per payer "in the last 24 hours" and said nothing about the tenant. That is not enough for a multi-tenant gateway: the loss a strike measures is the *seller's* answer served without settlement, so a block computed per payer alone would let one seller's strikes stop a payer at every other seller, and a clear one seller records would lift every other seller's protection. The query therefore joins `payments.endpoint_id` to `endpoints.seller_id` and filters both, and both directions are tests. **The count stays a query, not a column:** the payment row already says what happened, a counter beside it would be a second truth, and a `served_unsettled` row that later settles stops counting by changing state, which is the honest outcome. **The clear is an appended `payer_clears` row because `payments` is append-only evidence (PO-7):** deleting or re-stating a strike would erase the record of the seller's loss. `max(created_at)` for the pair becomes a watermark — strikes before it stop counting, strikes after it count again, and every clear keeps `cleared_by` and its note. The window remains a second exit; the documented exit is the clear, so the refusal carries **no `Retry-After`** — a date would promise something no timer is committed to. The status is **`403`, not `402`**, for the same reason C8's guards never challenge: the payer already holds a valid authorization, and nothing they sign can lift a seller's block. The block is evaluated **before** the window belt because it needs no configuration, and a misconfigured window must not turn a payer's `403` into a `503` that reads like our outage. No insert-time twin is needed: Guard 3 permits one in-flight payment per payer, so two strikes cannot be minted concurrently for the same payer. The seller-facing route is **not** in this row — F4 owns the route and UI-1 owns the operator identity it needs, and an unauthenticated clear endpoint would be the hole rather than the feature — so the action ships as `clearPayerBlock` and is tested through it.
- 2026-11-04: **C7: `abandoned -> verified` is legal, and the reason is a predicate rather than an argument.** C3 and C4 both declined this edge for the same worry — a row that can move back can presumably settle twice — and the worry dissolves once you separate the two things that make a payment. `replay_key` is the sha256 of the signed delegate action, so one authorization can only ever be *one* row; reuse therefore cannot produce a second payment, only a second attempt at the first one, and a payer who wants two payments must sign twice, which is C8's in-flight gate and C9's strikes. What a moved-back row must never do is settle on evidence that money already moved, and that is stated as data: the reopen's `where` clause carries `state = 'abandoned'` (the compare-and-set, so a row another writer moved in the window is not taken back over), `near_tx_hash is null and settled_at is null` (`REUSE_GUARD`, which is exactly the row C10's sweep can leave behind), and `endpoint_id = <this endpoint>` — necessary because the replay key does **not** include the endpoint, so without it one authorization replayed at path B would steal path A's abandoned row and be served for B's price. `served_unsettled` got no edge back on purpose: that row is goods delivered on credit, and a replay earning a second delivery is the loss this whole machine exists to prevent. Finally `advancePayment` refuses `to === "verified"` outright, so the checks cannot be bypassed by a call site that forgets them. **Consequence, and it is a test-quality finding, not a code one:** the first version of this row's mutation table had the deleted compare-and-set *surviving*, because `payments.test.ts` opens `postgres(url, { max: 1 })` and two `Promise.all` opens on one connection are a queue — that file proves conflict handling, never interleaving, and C3's "two requests with one authorization race" case should be read as a conflict-path demonstration for the same reason. Making the window real needed `select … for update` on a second connection (an uncommitted `UPDATE` blocks the retry on the index instead, at `wait_event = transactionid`, so the reopen never reaches its read). Pool-1 test files in this repo demonstrate *uniqueness*; pool-8 `guards.test.ts` is where concurrency is actually tested.

- 2026-11-04: **C6: a seller redirect is an answer, so it travels — with an absolute `Location`, and with Till never following it.** ARCHITECTURE 4.2 step 8 named the 3xx as unresolved and C4's code let it fall on the `502` side by default. Passing it through is the choice, for three reasons that each survive their own objection. (1) A `502` says the upstream failed; it answered, and the redirect is information about the resource the buyer paid to reach, so rewriting it into a gateway error destroys the only useful content. (2) Nothing is charged either way — settlement stays behind the 2xx gate — so the economic objection ("a redirect is not a delivery") is already handled by the state machine: the row is `abandoned`. (3) Forwarding a relative `Location` unchanged would be the broken option wearing a correct status: the buyer resolves it against **Till's** origin and gets a `404` from us, so a proxy must make it absolute (RFC 9110 7.3.2), and it is resolved against the endpoint's own `upstream_url`, which cannot send the buyer anywhere the seller did not already choose to send them. What is deliberately **not** on the table: following the redirect ourselves. That would dial a second, unvalidated address on the seller's say-so (C5 exists precisely because the address the seller names is not the address we vetted) and serve bytes this payment never bought. **Consequence, stated rather than hidden:** the seller's origin appears in a response header on the public gateway, so an endpoint whose upstream URL was meant to stay private cannot rely on that — a redirect is the seller publishing their own target. `docs/ARCHITECTURE.md` 4.2 step 8 and the section 10 failure row now say what ships, and section 10's row also stops promising that an `abandoned` payment can be retried with the same authorization, which was C7's and answered `409` at the time — C7 has since built that retry.

- 2026-11-04: **C8: Guard 2 is not re-implemented, and the row ships the ordering proof instead.** The task as written says "payer balance check", and the obvious implementation reads `ft_balance_of` in `guards.ts`. It would be a second chain call per paid request asking a question the same request just answered — `verify` already calls it on `delegate.senderId`, the account the signature binds, and refuses at `balance < amount` (S6 read the shipped facilitator, and `x402.test.ts` executes the boundary at exactly the price and one yocto below). Two checks that can disagree about a bound are worse than one, and the disagreement would be paid for in latency. What Till actually owns is *when*: the refusal must land before the seller is dialed, so the shipped artefact is a test that sends an underfunded genuine delegate and asserts `calls === ["verify"]` with the seller's hit counter unmoved, and the guard's comment names the file that enforces it rather than claiming the check. **Consequence:** `guards.ts` enforces two guards, not three, and D14's "verify does not hold funds" still leaves C9's strikes as the only defence against a payer who spends an authorization and never settles.
- 2026-11-04: **C8: one in flight per payer is enforced at the insert, behind a per-payer advisory lock, and the guard's read is only the polite half.** A guard that *reads* the table cannot be the gate: two authorizations arriving together both read "none", and S6 measured that the chain does not resolve it either — both verify, both submit, and the loser fails *after* the seller served. So `openPayment` gained a third argument (`InFlightClaim`), and inside one transaction it takes `pg_advisory_xact_lock(hashtext(payer)::int)`, re-reads that payer's live row and inserts, which is the only ordering that cannot book a second payment; the loser gets `{kind: "in_flight"}` and the route turns it into the same `429`. The lock is keyed on the payer, so two different payers never wait on each other, and `hashtext` is int4, so a rare collision costs a little waiting rather than correctness. **Consequence:** the race test has to be written to fail without the lock — `Promise.all` over two opens still interleaves favourably by luck of the event loop, and the first version of this test passed against a mutation that deleted the lock. What proves it is a holder transaction that leaves an *uncommitted* insert and sleeps: exactly the window where a read says "nothing in flight".
