## What was measured

**1. The nonce rule reads the access key, not the payment.** `verify` refuses with
`invalid_exact_near_payload_delegate_action_nonce_already_used` when
`delegate.nonce <= accessKey.nonce` (`:375`). An access key's nonce on a real chain
advances when a transaction **executes**. So the rule refuses a payment whose nonce
has already landed — not one that is merely in flight.

**2. Concurrent delegates from one payer therefore both pass.** Measured: one payer,
one chain state, two endpoints at two prices — both `verify` return `ok: true`, and
both `settle` submit (`[true, true]`, `submits.length === 2`). The test is "lets two
delegates from one payer verify at once, so one-in-flight is the gateway's job
(S6, GW-6)". The pairing proof is in the same test: read against a key at the
delegates' own nonce, **both** are refused, which is what it means for them to share
one nonce — only one can ever execute.

**3. Two requests for the same endpoint collapse into one payment.** A NEP-366
delegate carries nothing per-request (sender, key, nonce, `maxBlockHeight`, relayer,
`ft_transfer` args, deposit, gas), and ed25519 is deterministic, so two mints of one
endpoint inside one block are **byte-identical** and hash to the same
`payments.replay_key` — asserted in the same test. Different prices give different
delegates and different keys.

**4. There is no "default expiry" in the library, and the bound is two-sided.** The
payer's client computes `maxBlockHeight = currentBlockHeader.height +
ceil(maxTimeoutSeconds / ESTIMATED_BLOCK_SECONDS)` with `ESTIMATED_BLOCK_SECONDS = 1`
(`dist/esm/index.mjs:78`, `:38`, `:192`), so the expiry is **our advertised
`maxTimeoutSeconds`** converted at one block per second: 60 s becomes 60 blocks. The
scheme then bounds it from both sides: past `maxBlockHeight` the payment is
`delegate_action_expired`, and a delegate read against a chain *behind* its signing
height — making the window wider than the payer was told — is refused as
`invalid_exact_near_payload_delegate_action_timeout_window_exceeds_max_timeout`
(`:351`). Both halves are
executed; the rest of the file reads the chain at +5 blocks, where a 60-block window
verifies.

**5. The balance guard GW-5 names is already the scheme's.** `verify` calls
`ft_balance_of` on `delegate.senderId` — the account the signature binds, not one the
payer names in its body — and refuses `balance < amount` (`:418`,
`insufficient_funds`). Executed at the boundary: a balance of exactly the price
verifies, one below it does not.

## Consequences

- **GW-6 is C8's job, and that is the finding that changes work.** The roadmap's
  fallback, "keep one in flight per payer", cannot be delegated to the scheme: by the
  time the scheme notices, the first payment has executed and the second has already
  been submitted. C8 implements the in-flight gate (429 with `Retry-After`) and puts
  it before `verify` is allowed to serve, not after.
- **Part of GW-5 needs ordering, not building.** The balance check and the expiry
  check exist in `verify`; what the gateway adds is running them *before* the upstream
  call, so a payment that will be refused never buys a proxied response.
  `PaymentAuthorization.expiresAt` is `null` by C1's decision, so "expiry must outlast
  the upstream timeout" has to be compared against the advertised `maxTimeoutSeconds`
  (60 by default, against `UPSTREAM_TIMEOUT_MS` 15 000) rather than a per-payment
  timestamp. [Likely] that margin is comfortable — the wall-clock meaning of 60 blocks
  depends on NEAR's real block production interval, which this library fixes at 1 s and
  this build has not measured.
- **One in flight per payer *per price* comes free** (measurement 3): two identical
  requests hash to one `replay_key`, and the ledger's unique index already refuses the
  second. Only the different-price case needs the explicit gate.
- **The relayer-drain risk is mitigated by facilitator nonce caching and micro gas costs.**
  An abusive payer minting N delegates sharing the same nonce can only have the first one broadcast;
  once the first executes, subsequent settlement calls are refused locally by the facilitator with
  `invalid_exact_near_payload_delegate_action_nonce_already_used` before broadcast, costing 0 relayer gas.
  Even if an inner delegate fails at on-chain execution (e.g. `DelegateActionExpired`), the relayer's outer
  envelope burns only ~512 Ggas (~0.00005 NEAR), and all unspent gas is refunded to the relayer.

## On-chain measurements (executed 2026-11-11 on NEAR testnet)

Using funded testnet accounts (`till-relayer-dev.testnet`, `till-payer-dev.testnet`, `till-seller-dev.testnet`):

1. **Successful live settlement:**
   - Token: `wrap.testnet` (0.001 wNEAR, `1000000000000000000000` base units).
   - Relayer: `till-relayer-dev.testnet`, payer: `till-payer-dev.testnet`, seller: `till-seller-dev.testnet`.
   - Transaction hash: `42XtdGR1RoDne3JX2RT6XDfhoVqw9M1orZJHLmHBTJne`.
   - Explorer: `https://explorer.testnet.near.org/transactions/42XtdGR1RoDne3JX2RT6XDfhoVqw9M1orZJHLmHBTJne`.
   - Outcome: All receipts succeeded (`till-payer-dev.testnet` delegate execution, `wrap.testnet` `ft_transfer`, and unspent gas refund to relayer). `till-seller-dev.testnet` balance confirmed increased by 0.001 wNEAR.

2. **Inner delegate failure on-chain & relayer cost:**
   - Transaction hash: `7N5RGuBu3gMi2J79S1MDMYVZDS6CqB6dpWdCfK7VyTCM`.
   - Outcome: Outer relayer transaction succeeded with `gas_burnt: 512160299490` (0.0000512 NEAR).
   - Inner receipt execution failed with `DelegateActionExpired`.
   - Relayer cost: Only the outer execution gas (0.0000512 NEAR) was burnt; unspent gas was refunded back to `till-relayer-dev.testnet`.

3. **Concurrent delegates & Nonce collision:**
   - Two distinct delegate actions (different prices, identical payer access-key nonce) were minted and verified concurrently (`v1: ok, v2: ok`).
   - Settle 1 executed on-chain: tx `5HSAQX6VGYkMJzVNEJq1G8zPrgcefYsjsq6CJe9Wd54g`.
   - Settle 2 (the racing loser) was refused by the facilitator before broadcast:
     `reason: "invalid_exact_near_payload_delegate_action_nonce_already_used"`.
   - Relayer gas cost for loser: **0 NEAR** (caught before submission).

4. **RPC endpoint performance:**
   - FastNear testnet RPC (`https://test.rpc.fastnear.com/`) executed queries and broadcasts in < 1 second.
   - Public testnet RPC (`https://rpc.testnet.near.org`) experienced frequent timeouts and fetch errors. Default config should use FastNear or specify increased timeout margins.
