# S1 — Can an Intents deposit address be `payTo` for a NEAR x402 payment?

Date: 2026-11-03. Task: S1 [P0], Reqs: PO-3. Owner: either.

**Status: not measured on a chain. Closed by choosing the fallback the task's own
Done-when allows** ("a real small payment lands and the swap completes, *or the
failure is documented with the fallback chosen*"). The question is answered as far
as the code that would have to honour it answers it, and the residual risk is
named rather than waved away.

## Why no measurement happened

- `HACKATHON.md` Q-007: **NEAR Intents has no testnet and none is planned.** The
  only way to make a real deposit address and a real swap is mainnet.
- A mainnet measurement needs the money authorization, and A17 was answered
  **(c)**: the payout leg stays on the mock provider and the demo labels it.
  AGENTS.md allows a mainnet transaction only when the human asks for that
  specific action in the current session, with a stated ceiling; that ask was not
  made. No quote was fetched and no transaction was sent.
- A10's testnet accounts do not exist yet either, so even the NEAR-side half of
  the measurement (an `ft_transfer` landing somewhere) has no subject. That is a
  second blocker behind the first, not an alternative to it.

What *was* done instead, and it is not nothing: the payment path's own rules were
read out of the shipped implementation we are about to build on.

## The rule the implementation enforces

The exact-payment facilitator, before it accepts a payment authorization, runs:

```js
storageBalanceOf({ network, token, accountId: requirements.payTo })   // index.mjs:211
  -> callFunction(token, "storage_balance_of", { account_id: payTo }, { finality: "final" })
  -> { supported: true, registered: result != null }
  // a token without the method -> { supported: false }, and the check is skipped
```

and then (facilitator `index.mjs:238`):

```js
if (storageResult.value.supported && !storageResult.value.registered) {
  return this.invalid("invalid_exact_near_recipient_not_registered_for_storage", payer);
}
```

Three consequences, all [Known] from the above:

1. **`payTo` must already be registered for that token's storage, on the network
   the payment is made on.** Verification fails before any money moves, with a
   named reason, and there is no auto-registration anywhere in the package
   (`storage_deposit` appears zero times in its dist).
2. **A refusal is per-asset and per-contract, not global.** A token that does not
   implement `storage_balance_of` reports `supported: false` and the check is
   skipped, so an address could take one asset and be refused another.
3. **The failure is invisible to the seller until a payer hits it.** The rule fires
   inside `verify`, which runs on the buyer's request, so an unregistered `payTo`
   looks like a working endpoint right up to the first payment.

## The answer to the question asked

An Intents deposit address is a NEAR account that Intents controls for that user,
and Till does not control its storage state. Combining consequence 1 with that
fact: **using an Intents deposit address as `payTo` is only possible for an asset
the Intents side has already registered that address for, and nothing in our stack
can make that true.** Whether Intents registers them is not knowable from our side
and was not measured. [Likely] it does not register for every NEAR fungible token,
because it cannot know which token a seller will pick; [Guessing] is the only honest
label for whether it registers for the ones it advertises.

So the answer that unblocks the build is the negative one, and the fallback is the
one the task anticipated.

## The fallback chosen

**`payTo` is the seller's own NEAR account on `near:testnet`, and the payout leg
runs on `PAYOUT_PROVIDER=mock` (or `direct`, which is the same shape without a
provider).**

- The x402 leg — challenge, verify, proxy, settle, ledger — is fully exercisable
  without Intents at all, because the recipient is an account we control and can
  register.
- The cross-chain leg is demonstrated on the mock provider, and every mocked
  outcome already carries `simulated: true` in `swaps.raw` (D2), so the line between
  mocked and real stays machine-readable rather than a caption on a slide (DQ-2).
- **New requirement this spike produced, and it is the useful part:** endpoint
  creation must check the registration rule *before* the seller publishes a price,
  because consequence 3 means an unregistered `payTo` fails only on a buyer's
  request. That belongs to D4 (PO-1), and D4's row now says so. Until D4 exists, a
  testnet seller can create an endpoint that cannot be paid.
- S7's question ("does registering a new token cost the payer or the recipient") is
  **not** answered here. It is still a real mainnet question and it still waits on
  A17, but its practical urgency drops under this fallback: with a seller-controlled
  `payTo`, registration is a one-time action on one account rather than a property
  of an address we do not control.

## What would verify the measured answer, in order

1. A10: three testnet accounts (relayer, seller, payer) with the relayer funded —
   testnet NEAR is free, so this needs no money authorization.
2. A17 reopened as (b): a stated ceiling of tiny mainnet amounts, from accounts the
   human creates, on separate dev accounts as `HACKATHON.md` advises.
3. Then the measurement itself: quote `/v0` with the NEAR token as the *destination*
   chain, take the deposit address it returns, use it as `payTo`, and read
   `storage_balance_of` for it on that asset's contract before and after a minimal
   transfer. The spike is closed by real evidence when that call returns non-null
   for an address Intents issued, or the payment is refused with
   `invalid_exact_near_recipient_not_registered_for_storage`.

Until step 2 happens, this file documents a decision, not a measurement.
