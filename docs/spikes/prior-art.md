# Prior art — does seller-side x402 reconciliation on NEAR already exist?

Date: 2026-11-03. Task: ROADMAP item B1 [P0] ("Prior art search: GitHub, NEAR Discord and DevHub for existing seller-side x402 reconciliation on NEAR"). Reqs touched: risk row "Another entrant builds the same idea" (PRD §12), ARCHITECTURE §14.4. Owner: agent. Research-only; no repo other than this file was modified and no code was changed.

## Bottom line (answer to B1)

**No existing project does what Till's headline does: seller-side reconciliation that matches each NEAR x402 payment to its NEAR Intents / 1Click cross-chain payout by transaction hash and raises discrepancies when they disagree.** That exact combination was not found. [Likely] — based on the searches below, and search-absence is weak evidence, so read "not found" not "does not exist".

What *does* exist falls into four buckets, none of which is Till:

1. **Our own Stellar back-office (`accensa/accensa-app` + `accensa-contracts`)** — the single closest thing to Till anywhere. It is (a) Stellar, not NEAR, (b) built on custom Soroban contracts (which Till forbids), and (c) it **already has payment↔chain reconciliation**: `scripts/reconcile-payments/` rebuilds the ledger-derived columns of `payments` from the Stellar ledger with a decoder that deliberately does not share code with the indexer, diffs them row by row, prints `RESULT: DISCREPANCY FOUND` on any mismatch, and is wired to a daily scheduled GitHub Action. What it does **not** have is the outbound leg: its only "payout" words are `RefundVault` float withdrawals, so there is no payment↔cross-chain-swap matching by transaction hash. It proves the thesis, supplies the reconciliation posture Till keeps, and the gap after it is precisely the Intents payout leg. Per `HACKATHON.md` Q-002/Q-005 it is baseline design knowledge, not reusable NEAR-window code.
2. **x402 reconciliation on other chains** — `nirholas/three.ws` (Solana) genuinely reconciles "a settlement that silently failed" against on-chain signatures, which is the *same failure class* as Till's `SERVED_NOT_SETTLED` / `PAYMENT_NOT_SWEPT`; `daydreamsai/lucid-agents` and `ItachiDevv/ClawVille` use the word "reconciliation" for lighter things (idempotency-key checks; a metaverse economy sweep). None is NEAR, none has an Intents payout leg.
3. **NEAR x402 building blocks (no seller ops)** — `fastnear/x402-facilitator` (Rust facilitator), `r-near/x402-near-demo` (settle-first gateway demo), `mikedotexe/near-payment-agent`, and the buyer-side hackathon entry `Gliana-Labs/gliana-near-x402` ("Saku"). These are the pieces Till *assembles*; none is the back office.
4. **Generic fintech reconciliation** (Paddle, Tipalti, Naya) — confirms "payment reconciliation" is a standard, expected capability for real businesses, which is exactly the Real-World Money track's ask, but none touches x402 or crypto payouts.

**Recommendation** (not a fact): the reconciliation engine (LR-1…LR-8), the settle-only-on-2xx ordering with guards (GW-3…GW-8), and the Intents-payout-by-hash match (D13/LR-2) remain Till's defensible core. Build *on* existing pieces (facilitator, Intents 1Click) and *differentiate* on the payment↔payout discrepancy rules, which no found project implements. Details in "What it means for Till".

## Findings — closest to Till

### 1. `accensa/accensa-app` + `accensa-contracts` — our own Stellar merchant back-office [Known]

Read from two vantage points: the repo through `gh api` (README, file listings), and the working clone at `../accensa-app`, whose checkout `bba7a88` is dated 2026-10-05 while GitHub reports `pushed_at` 2026-10-26 — so the clone may miss ~3 weeks of upstream commits, and anything below marked "grepped locally" carries that caveat (the `scripts/reconcile-payments/` listing was re-fetched from `main` to confirm it is current). 19★ / 22★. Same problem statement almost word-for-word as PRD §2: an x402 paywall moves payment off the seller's database and "your database never hears about it", leaving "no revenue view, no attribution, no way to answer a dispute." Structure: **indexer** reconstructs payments from Stellar SAC transfers, **SDK** (`attachAccensaHook`/`createSettleHook`) attributes each payment to the route, **dashboard** shows payments/totals/receipt verification, **webhooks** with retry policy, Postgres ledger cursor, and **`scripts/reconcile-payments/`** (cli/db/decode/diff/rebuild/rpc/trust-boundary, each with tests) driven by `.github/workflows/reconcile.yml` on a daily cron. On-chain half is two **Soroban contracts**: `ReceiptAnchor` (Merkle-batched verifiable receipts) and `RefundVault` (policy-bounded float).

Overlap with Till: the seller-back-office frame, append-only ledger, dashboard, CSV-style accounting intent, webhook delivery, "never invents rows" honesty — and, more than the earlier draft of this file admitted, **the reconciliation mechanism itself**. `reconcile-payments` rebuilds chain-derived columns independently of the indexer, diffs them row by row against production, documents a provenance trust boundary (`tx_hash`/`amount` from chain are checked; `route`/`request_id` are merchant-reported and explicitly out of scope), and its README argues that "a reconciliation nobody runs is the same as no reconciliation" on the strength of a seven-day unnoticed indexer outage. That is Till's `PAYMENT_NOT_SWEPT` / `ORPHAN_DEPOSIT` shape and its S8/sweep posture, already built and already reasoned about — for Stellar SAC transfers. **Does not overlap**: (a) it is Stellar, not NEAR; (b) it relies on custom contracts, which Till forbids (PRD §4 non-goals, D3, AGENTS hard rule 1); (c) it has no outbound leg. Grepped locally for `payout`: every hit is either a `RefundVault` float withdrawal ("The merchant deposits a float to the `RefundVault` contract … the merchant triggers a payout from the dashboard") or a notification label, never a swap — so there is **no payment↔cross-chain-payout matching**. Till's LR-2/LR-3 (PAYOUT_REFUNDED/STUCK/FAILED, PAYMENT_NOT_SWEPT), the Intents/1Click `PayoutProvider`, and match-by-tx-hash across two chains (D13) are absent here even in our own prior work. Per `HACKATHON.md` Q-005 "own old libs count as baseline" and Q-002 "only the NEAR integration built in the window is judged," this is design knowledge to reuse, not code to port; PRD §10 ("reuse design knowledge from earlier work, not earlier code") applies. Note the nuance for the README honesty rule (DQ-2): the two projects share an org, a thesis and now a reconciliation pattern, which a judge may read as "same product, new chain." Differentiate explicitly, and say plainly that the carry-over is the *method* while the *payout leg* is what Till adds.

### 2. `nirholas/three.ws` — `api/_lib/x402/revenue-reconciliation.js` (Solana) [Known]

Fetched and grepped the file body. This is the most conceptually similar artefact found. It reconciles the platform's own inbound revenue: a table `agent_payment_intents` ("inbound revenue (user → agent payments)") of payments the platform marked settled, then **"verifies each Solana settlement signature on-chain"** to catch "a settlement that silently failed," with states `confirmed | failed_onchain | missing_onchain | missing_signature | skipped_non_solana`. That is precisely the failure class of Till's `PAYMENT_NOT_SWEPT` and `SERVED_NOT_SETTLED`, and it matches by on-chain signature, not amount/time — the same integrity stance as D13/LR-2.

But: **Solana/EVM only** (it explicitly skips non-Solana), no NEAR, and critically **no cross-chain payout** — it checks that a payment landed, not that a payment converted into the seller's chosen asset on another chain. It is an internal batch job on the operator's own revenue, not a productised seller dashboard with discrepancy findings, severities and suggested actions (LR-4/UI-4). Verdict: strong evidence the *reconciliation idea* is real and wanted; a genuinely different (and narrower) implementation. [Likely] there is no NEAR equivalent of this file, since NEAR+Intents+reconciliation code search returned nothing.

### 3. `fastnear/x402-facilitator` (Rust) + the NEAR facilitator ecosystem [Known]

Fetched README. "Production Rust facilitator for x402 `exact` payments in Circle USDC" supporting `near:testnet`/`near:mainnet` via NEP-366 delegate `ft_transfer`, with "exactly-once claims, sponsorship budgets, PostgreSQL journaling, crash recovery, chain-specific terminality." It is also run as the hosted reference at `https://x402.mikedotexe.com/` (listed in the fetched x402.org facilitators doc; that URL was read from the doc, not independently fetched — [Likely]). Other facilitators in the same list (AlgoVoi, Solvador) cover NEAR too.

This overlaps Till's *facilitator/verify/settle* layer and even its ledger-ish "journaling," but it is the **protocol/execution** layer, not the seller operations layer: no endpoints, no payout routing, no Intents, no discrepancy rules. Till deliberately does **not** use this Rust service — ARCHITECTURE D2 uses the JS `@fastnear/x402` package in-process — so this is an *alternative* facilitator, not a competitor. It confirms the "you can self-host a NEAR facilitator" premise our design depends on, and that "Circle USDC on NEAR" is the live asset (relevant to PRD §13 open question 5). [Known] from README.

## What it means for Till

**Genuinely new for NEAR (keep, and pitch hard):**
- The payment↔payout reconciliation *for a cross-chain payout*. LR-1…LR-8, rules in PRD §7 (`SERVED_NOT_SETTLED`, `PAYOUT_REFUNDED`, `PAYOUT_FAILED`, `PAYOUT_STUCK`, `PAYMENT_NOT_SWEPT`, `PAYMENT_UNBOOKED` at P0 — the sixth is G6·2's, added after this spike was written; `PAYOUT_SHORTFALL`, `INCOMPLETE_DEPOSIT`, `ORPHAN_DEPOSIT` at P1). The *method* is not new to this team — `accensa-app/scripts/reconcile-payments` already rebuilds payments from chain, diffs them row by row and fails a scheduled job on mismatch — but no NEAR project, and not our own Stellar app, applies it to an outbound Intents swap.
- Match by transaction hash across the x402 payment and the Intents swap (D13/LR-2). `three.ws` verifies settlement on Solana but never matches a payment to a *cross-chain payout*.
- Settle-only-on-upstream-2xx with the four guards (D7, GW-3…GW-8) as a hosted gateway. The NEAR demo `r-near/x402-near-demo` settles first; the facilitators don't proxy at all.
- The end-to-end seller audit trail "payment → NEAR tx → Intents swap → destination-chain tx" with plain-language discrepancies (G2/G3, LR-4, UI-4).

**Reuse / build on top of (do not reinvent):**
- Facilitator + verify/settle: keep D2 (in-process `@fastnear/x402` over `@x402/near`); `fastnear/x402-facilitator` and the hosted `x402.mikedotexe.com` prove the layer exists and are the fallback if the JS package's self-host path has gaps.
- x402 v2 protocol surface (GW-1) from `x402-foundation/x402` / `docs.x402.org` — no protocol invention (AGENTS hard rule 1).
- NEAR Intents + 1Click for payouts (PO-3) — nothing found wraps 1Click in a *seller reconciliation* product, so the `PayoutProvider` (D4) is new glue, but the 1Click API and `near/intents` are the documented rails (S5 already mapped them).
- Indexer/dashboard/webhook patterns from our own `accensa-app` (design knowledge only; not window code) — the "reconstruct revenue from chain, never invent rows" posture (DQ-2) carries over directly.
- The reconcile-sweep cadence shape from `ClawVille`'s auto-reconcile reinforces our 60 s loop; the settlement-verification-by-signature pattern from `three.ws` reinforces LR-2's integrity stance.

**Recommendations (explicitly recommendations, not facts):**
- R1 (spikes/phase D1–D2, PRD §12 risk row): No scope change warranted — the reconciliation engine stays the product. Update the risk "Another entrant builds the same idea / [Guessing] that they have not" from ARCHITECTURE §14.4 to "[searched 2026-11-03: closest is our own Stellar back office (no payout reconciliation) and Solana `three.ws` (same failure class, no cross-chain) — NEAR seller-side payout reconciliation not found]."

Skipping this risks a judge reading it as "same product, new chain," the one real originality threat found.
- R3 (GW-3/D7): Keep settle-after-serve. `r-near/x402-near-demo` is the counter-example (settle-first); cite it in the README as the naive design Till's guards fix.
